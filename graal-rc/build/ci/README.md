# Windows CI/release checks

The workflow in `.github/workflows/windows-ci.yml` has these gates:

1. Go dependency verification, `go test ./...`, `go vet`, and `staticcheck`.
2. `npm ci`, `npm audit --audit-level=high`, Wails binding generation, and `npm run build`.
3. Native FFI compilation with `CGO_ENABLED=0`, including PE-bitness checks for `rclib`.
4. Windows `amd64` and `386` builds, each published with a `SHA256SUMS.txt` manifest.
5. NSIS installer compilation when `makensis` is present. The WebView2 bootstrapper is
   generated by Wails for that validation.

The published NSIS installer is machine-wide and installs to
`C:\Program Files\RuanFernandes\Graal Remote Control`. This is intentional: it is the
legacy location used by pre-3.1 releases, so an upgrade replaces the existing executable
and shortcut instead of leaving a second per-user installation. Installation and
automatic updates therefore request administrator approval. User data remains under
`%LOCALAPPDATA%\graal-rc` and is not removed by the installer.

The repository ships the native grclib matrix under `rclib/native/<os>-<arch>/`, fetched
from the pinned `GScript.GRClib` release. The pipeline always selects the matching native
library and never substitutes a different architecture into an artifact. The legacy flat
files under `rclib/` remain only as development fallbacks.

The upstream `v1.0.46` source contains the class-response parser correction for
`PLO_NC_CLASSGET`. After refreshing the matrix, the release workflow packages the six
architecture-specific libraries directly from that pinned release and does not apply a
local native workaround.

The checked-in Wails `v3.0.0-alpha2.117` dependency has an upstream 386 compile error in
its updater package (`2 << 30` passed as `int`). The x86 build script uses a disposable
`-modfile` replacement to `v3.0.0-alpha2.118`, which contains the upstream `int64` fix; it
does not edit the repository's `go.mod` or `go.sum`. This can be removed when the project
upgrades its checked-in Wails dependency.

`go vet` runs with `-unsafeptr=false` because the FFI boundary intentionally converts ABI
return words to native pointers. The FFI script still runs `go test -c`, checks that the
package has no cgo files, validates the native PE machine type, and runs vet on `rclib`.
The same analyzer also reports one existing Windows crash-handler conversion, so the
exception is scoped to that analyzer rather than pretending every unsafe conversion is FFI.
Other vet analyzers remain gates.

The current codebase also has an established staticcheck baseline for `ST1000`, `ST1005`,
`U1000`, and `SA2001`. Those four checks are excluded explicitly in the workflow command;
all other staticcheck diagnostics fail the job. Runtime code was not changed to create this
CI configuration.

The WebView2 smoke test is intentionally opt-in because hosted Windows runners may not
provide a usable interactive WebView2 desktop session. It validates the machine-wide
Program Files installation. Run the workflow manually with
`run_webview2_smoke=true` after the NSIS gate has produced an installer. If NSIS is not
installed on the runner, installer validation and the dependent smoke job are skipped with
a notice rather than requiring secrets or failing a pull request for missing tooling.

Local examples from the repository root:

```powershell
go run ./build/ci/fetch-grclib -root . -check
pwsh -File build/ci/generate-bindings.ps1
pwsh -File build/ci/verify-ffi.ps1 -Architecture amd64 -RunStaticcheck
pwsh -File build/ci/build-windows.ps1 -Architecture amd64
pwsh -File build/ci/build-windows.ps1 -Architecture 386
```

To refresh the native matrix from a newer upstream release, run:

```powershell
go run ./build/ci/fetch-grclib -root . -release v1.0.46 -force
```

The fetcher resolves the six expected release assets, extracts only the
architecture-specific library, records SHA-256 values in
`rclib/native/manifest.json`, and refuses a release with a missing asset.
